## Counter definitions

The Overview reads `TownWorld` and transient `TownSession.runtime`, not SQL aggregate queries. Live worlds are loaded from `living_towns.world` JSONB through the authenticated repository. The SQL projection also maintains residents, houses, plots and districts; gift groups remain in world JSONB. Simulator worlds exist only in browser memory. Demo reset/regeneration discards that demo's counters; it never resets live records.

## Identity and event behavior

| Case | Observed behavior | Assessment / recommendation |
| --- | --- | --- |
| Follow then subscribe | Same resident by `twitchUserId`; follower flag remains true; one house allocated. | Matches rule. |
| Subscribe without recorded follow | Creates subscriber resident with `isFollower: false`; housing permitted. | Matches rule; do not fabricate follow evidence. |
| Repeated follow/subscribe | Same event ID is deduplicated. Different IDs for the same user do not duplicate resident/house; repeated follow does not repeat arrival once follower flag is true. | Matches permanent identity rule. A repeat subscription can replenish the housing reserve if growth was previously deferred. |
| Resubscribe | Same house/person; cumulative months uses maximum, not addition; fresh event IDs can emit new welcome-back effects. Live resub message rechecks current membership through Helix. | Event-ID idempotency is not a promise to suppress all later legitimate celebrations. |
| End subscription | Membership becomes inactive; existing home/customization retained with legacy status. An unknown identity gets a neighbor record even with no prior residence. | Retained property is intended policy. Decide separately whether an unknown end event should create a visible resident. |
| Same person, different towns | Independent resident/house per town. SQL keys `(town_id, twitch_user_id)` and unique `(town_id, owner_twitch_user_id)` allow this. | Existing persistence/multi-town tests cover isolation. |
| Visible arrivals / visitors | Simulation resident actors cap at 24. Raids create a temporary effect, not durable people. Live empty worlds/OBS can contain four ambient scenery actors. | Never count graphics as permanent residents. |
| Reload / refresh | `createSession(savedWorld)` starts with no effects/tasks; durable receipts prevent event reapplication. Loaded resident actors start at Town Hall and walk again. Same-world live updates preserve runtime. | Data is not duplicated. But apparent entrances can recur, and a full remount can replay still-buffered reactions (below); the strict “no visual replay” rule is not fully met. |

Live persistence uses server-only verified adapters, validated payloads, owner-derived town lookup, durable per-town event receipts, revision conflict retries and transactional commit/projection. The `source: "twitch_verified"` marker itself is **not** verification; the authenticated/scoped adapters and registered EventSub subscription checks are the trust boundary. No HTTP endpoint accepts arbitrary simulated town events. Existing persistence tests cover concurrent allocation, cross-town ownership, reload and duplicate deliveries.

## Exact construction and growth sequence

`createWorld` maps 12 generated houses to `plot-1` through `plot-12` across six starter blocks. `plot-expansion-1` and `plot-expansion-2` are initially vacant in the reserve district named “New beginnings.” Followers consume no housing capacity.

The allocation order in `engine.subscribe` is **vacant original reserve plot → existing unclaimed house → other vacant plot**. Therefore subscribers 1 and 2 construct houses 13 and 14. Subscribers 3–14 reuse starter homes. This does not match an “always reuse existing unassigned houses first” policy, but it is explicit existing behavior and already tested. No change made.

`PLANNING.reserve = 4`. Before allocating a homeless subscriber, the engine attempts to provide at least one available slot; after allocating (also when a subscriber already owns a house), it attempts to restore at least four slots. The expansion condition is strictly **available capacity < 4**, not <=4 and not “fewer than four empty plots.” Starting from a fresh town, subscriber 10 leaves four available starter homes and no expansion. Subscriber 11 leaves three, then adds one district with 12 vacant plots: **26 plots, 14 built homes, 11 owned homes, 15 available slots**. Subscriber 15 constructs the first home in that new district: **15 built homes, 26 plots**. Expansion itself constructs no houses.

Each deterministic spiral district adds 12 plots, connecting roads/navigation and scenery. Existing geometry, district records, property identities, owners, customization and Mayor settings remain; tests cover all 40 permitted added districts, navigation, overlap and transactional rollback. Maximum capacity is `14 + 40*12 = 494` plots. Growth failure/cap does not erase existing homes; allocation uses remaining capacity or waitlists the subscriber. Later sync can retry; growth is not triggered by chat, followers or an unresolved aggregate gift.

**Neighborhood recommendation:** do not simply add one to the current counter and claim it counts district records. There are already seven residential district records (six built blocks plus a reserve), not one. Choose a product definition first: (a) generated expansions, current value 0; (b) residential districts, initial 7 including reserve; or (c) settlement regions, initial core = 1 plus generated districts, requiring an explicit aggregation definition. Keep current UI pending that separate decision.

## Community Gifts

The actual simulator button is **“Gift 2 subscriptions”**, not a five-gift button. It submits one `GIFT_SUBSCRIPTION` with a new group ID, a synthetic giver and **two known recipients**. It both announces a batch and immediately subscribes those recipients. “Replay gift recipients” emits individual `NEW_SUBSCRIBER` events with the same group correlation; group recipient-ID checks and identity allocation prevent double counting/housing. Five-recipient coverage was added in tests without changing that UI.

Existing followers upgrade in place; existing subscribers retain their home. A giver does not become a resident or receive a house merely for gifting. An anonymous giver is supported. A batch without recipients increases gifts and creates its thank-you effect, but does not invent users or construct houses. The engine reconciles identified recipients only when a caller supplies the same group ID. There is no unresolved-recipient timeout, fabricated identity or separate UI pending-gift count.

The live adapter maps `channel.subscription.gift` to an aggregate with `groupId = eventsub:<notification ID>` and `recipients: []`, then starts subscriber sync if no job is already running. `channel.subscribe` and Helix membership independently identify actual users and entitlement. This implementation does **not** correlate those members back to a gift batch; live `recipientIds` can stay empty after every real recipient has been housed. Gift totals therefore cannot be used to infer missing houses. Delivery retries with the same notification ID are deduplicated; a new notification ID is a new aggregate group. If a sync is already running, the aggregate does not queue another one; later verified events/manual sync may be needed to catch a membership change missed by that scan.

Sync publishes neighborhood expansion presentations only; it intentionally suppresses a storm of imported-member housewarming effects. Consequently a gift recipient first discovered through sync can get a permanent house without a separate live arrival/housewarming celebration. The aggregate thank-you is independent of this.

## Mayor and OBS

Sources: [engine](src/lib/simulation/engine.ts), [behavior](src/lib/simulation/behavior.ts), [renderer](src/lib/rendering/create-renderer.ts), [overlay reactions](src/lib/overlay/reactions.ts), [playback](src/lib/overlay/playback.ts).

| Event | Overview/simulation behavior | Current live ingestion / OBS behavior |
| --- | --- | --- |
| Chat | Higher movement speed `(36 + score*0.45)` and shorter pauses; no event-specific celebration. | Live `channel.chat.message`; sanitized activity reaches both OBS modes. |
| Follow | Arrival effect on first follow; no explicit Mayor task. | Internal/simulator support only; no live follower subscription. |
| New housed subscriber | Housewarming effect; Mayor routes to entrance, then celebrates four seconds. | Live `channel.subscribe` plus verified Helix sync. EventSub effects map to subscriber OBS reaction; bulk sync suppresses housewarming presentations. |
| Resubscription | Welcome-back effect and house celebration task, preserving property. | Live `channel.subscription.message` with entitlement recheck; OBS welcome-back reaction. |
| Gifts | Aggregate thank-you effect alone does not enqueue a Mayor task; identified new housing does. | Live `channel.subscription.gift`; OBS maps gift effect to generic celebration. Thus Overview and OBS are not identical reactions. |
| Expansion | Neighborhood effect plus welcome task at its road node. | Verified allocation/sync can publish neighborhood reactions to OBS. |
| Subscription end | Retains legacy home; no special reaction. | Live `channel.subscription.end`, also reconciliation. |
| Raid | Temporary Town Hall effect and priority welcome task; no permanent residents. | Simulator only. `raid` exists in OBS reaction types but `reactionFromEffect` does not map it and no live raid subscription is installed. |
| Bits / donations | No internal event processor cases. | OBS labels/priorities are placeholders, not live integrations. No provider ingestion or distinct animations. |

Overview uses bounded effects (32) and Mayor tasks (16 in the ordinary task helper), deduplicating task destinations within a processed session; raids insert at the front and replace hall tasks. Tasks expire; expansion tasks last up to ten minutes, ordinary visits two minutes, raids 20 seconds. Live Overview appends presentation tasks to its own bounded runtime; it does not merge destinations across separate presentations.

OBS has a separate priority `ReactionQueue`: up to 32 pending, last 256 seen IDs, expired items discarded, higher priority interrupts, equal/lower waits, up to six seconds per reaction. Interrupted reactions are not resumed. Subscriber/resub/gift/neighborhood labels all use the existing generic celebration animation; they are not separate bespoke animation clips.

Living Town and Spotlight share one playback/session model and renderer logic within a browser source. Spotlight changes composition and shows a foreground Mayor driven by that state. Separate OBS browser sources and the Overview run independent transient clocks, movement and queues; they do not share one authoritative Mayor position or necessarily identical reaction timing.

## Confirmed limitations and follow-up scope

1. **Visual replay after full refresh:** `SubscriberHousing.shown` is a component-local set (128 IDs); OBS `ReactionQueue.seen` is local to playback. The server retains presentations for 15 seconds. Refreshing/remounting during that window can celebrate the same presentation again. Polling within the existing instance is deduplicated; persisted residents/houses are safe. A new playback cursor/start-time policy needs a separate implementation prompt and tests; reconnect-without-remount tests do not prove refresh safety.
2. **Visible population is not roster synchronization:** `createSession` positions up to 24 residents at Town Hall. Live same-town reload replaces `world` but does not rebuild `runtime.residentActors` for newly added residents. Ambient actors are not identities. New live membership can update counters/house effects without a corresponding new walking actor. Address actor reconciliation separately if that visual guarantee is desired.
3. **Terminology differs across pages:** subscriber-owned includes legacy; available plots includes unclaimed buildings while management free plots does not; neighborhood counters use different models. Choose definitions before a consolidated UI change.
4. **Gifts are observed quantities, not unique recipients or lifetime totals.** Live batch-to-recipient reconciliation is absent; do not label empty `recipientIds` as unfulfilled entitlements. Consider explanatory copy, not speculative allocation.
5. **Event presentation is transient/bounded:** refresh replay, dropped/expired buffered effects, server restart and long queues mean visual delivery is not exactly once. Bulk imports intentionally omit arrivals. Permanent membership/ownership has stronger receipt/transaction guarantees.
6. **Missing live reactions require distinct implementation:** followers, raids, Bits, external donations and bespoke Mayor behaviors need adapter/permission/product decisions. No new scopes or reactions were introduced by this audit.

No confirmed permanent identity duplication or house-loss defect was found in the audited paths. The separate UI, replay, actor and reaction recommendations above are not implemented or claimed fixed.
