# Technical decisions

## 2026-10-27 — Secure Twitch account connection

These decisions supersede the foundation's no-authentication/no-secrets scope. Existing Mayor behavior, renderer, generation and event simulation are preserved.

1. **Use Twitch's server-side Authorization Code flow.** The registered application is Living Town. Credentials and code exchange stay in the Node runtime. Request an empty scope list and use Helix Get Users for basic identity; no email, chat, moderation or subscription permissions. Verify the token's client ID and numeric user ID before accepting the profile.
2. **Separate browser binding from OAuth state.** Generate independent cryptographically random 256-bit state and HttpOnly browser binding values. Store their HMAC digests server-side for ten minutes, with atomic consume-before-exchange semantics. Failed/denied callbacks also consume the attempt. Never accept caller-supplied redirect destinations or expose upstream error details.
3. **Choose server-side sessions, not client-carried OAuth tokens.** The server-storage alternative avoids a JWT/session library for this deliberately ephemeral phase. A browser receives only a random 256-bit session ID, while the memory store retains its keyed digest. Eight-hour absolute expiry bounds access; fresh login rotates the browser session. Cookies are host-only, HttpOnly and SameSite=Lax; production uses Secure `__Host-` cookies and requires an HTTPS redirect.
4. **Encrypt tokens even in the temporary store.** AES-256-GCM uses fresh 96-bit nonces and session-record-specific associated data. HKDF derives separate encryption and HMAC keys from a random 32-byte base64 `SESSION_SECRET`. Access and rotated refresh tokens stay server-side. The authenticated payload is not placed in a browser cookie. No credentials are logged or committed.
5. **Validate maintained sessions independently of browser activity.** Validate on login, startup re-entry and stale reads. A one-minute background scheduler checks the 30-minute freshness threshold, leaving margin inside Twitch's hourly requirement. Cap sessions at 200 and batch checks with bounded concurrency. Authorization guards force a fresh check. Unexpected revocation or a validation outage fails closed. After a known expiry, refresh reactively on an invalid-token response, validate the replacement and retain its rotated refresh token. Concurrent reads of a session share validation work.
6. **Sign out locally before remote cleanup.** Require a same-origin POST with a session-bound CSRF token. Invalidate all sessions sharing the access token and attempt Twitch revocation. Failures enter an encrypted, in-memory retry queue for up to one hour; process shutdown loses that queue. A late validation response cannot resurrect a removed session.
7. **Treat authentication, ownership and subscription as separate facts.** Both streamers and viewers use the same login. Stable Twitch IDs identify accounts; display names and broadcaster profile types grant nothing. `requireTownOwner` validates the session, loads the specified town from a trusted repository and compares its streamer ID. The demo remains public and synthetic; no ownership is assigned on login and no active subscription is inferred. Future mutation endpoints must invoke the guard and their own CSRF protection.
8. **Retain explicit runtime limits instead of adding persistence.** Auth supports one continuously running Node process. Restart or secret rotation invalidates all sessions. Production scaling/serverless needs atomic shared session/state storage, refresh coordination, validation scheduling and durable ownership before deployment. Supabase, live EventSub and backend town mutations remain out of scope.
9. **Keep identity out of static town state.** A small client account widget fetches only the public profile and logout CSRF value from a no-store endpoint. `/account` adds profile and safe error messages. The town's build-time simulator gate and renderer lifecycle remain unchanged. Next dev logging excludes callback URLs; hosting/proxy logs must separately redact OAuth query strings and authorization data.
10. **Test the security boundary without real credentials or browser automation.** Inject clocks, Twitch clients and memory stores. Test state/replay, HTTP cookie protections, callback failures, expiry, encryption tampering, refresh/revocation races and cross-town authorization. Preserve all original simulation/generator tests. A real login and Chrome regression checks are manual.

References: [authorization code flow](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/#authorization-code-grant-flow), [token validation](https://dev.twitch.tv/docs/authentication/validate-tokens/), [refresh](https://dev.twitch.tv/docs/authentication/refresh-tokens/) and [revocation](https://dev.twitch.tv/docs/authentication/revoke-tokens/).

## 2026-10-27 — Town functionality and event simulation

These decisions extend the foundation below; simulation behavior is now owned by the domain layer rather than the renderer.

1. **Keep the Town Overview.** Preserve the generator, original 12 home coordinates and procedural visual language. No isometric renderer or major redesign.
2. **Separate durable world from transient runtime.** `TownWorld` carries schema/generator versions, town/streamer identity, layout, districts, plots, buildings, ownership, residents, Mayor identity and delivery/gift ledgers. `TownRuntime` carries activity, actor behavior, effects and clock. Both are JSON-safe; only the world crosses the future persistence boundary.
3. **Use world coordinates and semantic appearance.** Camera scaling never changes model coordinates. Colors, architecture and decoration IDs are asset-independent. `overviewOf` translates the shared model to the original graphics shapes; future renderers can project the same world.
4. **Pure events and explicit time.** `processEvent` returns a new session and outcome; `tickTown` advances behavior/decay with an injected clock. Neither imports React, PixiJS nor browser APIs. The React demo updates at 100 ms; PixiJS interpolates presentation independently.
5. **Stable ownership and finite capacity.** Fill two expansion plots, then assign original unclaimed demo homes without relocation/restyling. One home per Twitch user per town. At 14 owners, keep subscribers on an explicit waitlist instead of moving buildings or inventing terrain. Resubscriptions reconcile missing initial records and keep maximum cumulative months.
6. **Delivery and semantic deduplication.** Persist processed event IDs in the world snapshot and retain owner uniqueness independently of event ID. Retried deliveries return the original result marked duplicate, with no new effect. Production will need transactional uniqueness and an event retention policy; the in-memory ledger is intentionally unbounded for this demo.
7. **Explicit gift correlation.** A stable group ID joins aggregate and recipient events. Count each group using maximum announced total versus unique identified recipients. Do not create recipients for anonymous aggregates or correlate by timing alone. The future Twitch adapter must establish trustworthy group IDs; there is no live adapter yet.
8. **Anti-spam activity.** A 60-second linearly decaying window, one credited message per user per 10 seconds, identical normalized-message suppression, and a 100-point cap. Transient samples hold normalized text; world snapshots do not. Activity increases resident/Mayor movement and reduces idle pauses.
9. **Mayor remains the companion.** Graph routing and task transitions live in `behavior.ts`. The renderer shows wandering, approach and celebration states. New homes enqueue visits; raids briefly prioritize Town Hall. Runtime queues/effects are bounded, and reduced-motion users see static actor presentation while logical state continues.
10. **Production simulator opt-in is explicit.** Server-provided gate: development, or `TOWN_DEMO_MODE=true` during build. No public event endpoint exists. A future backend must enforce authorization independently; a demo flag is not a security boundary for durable writes.
11. **Temporary in-memory persistence boundary.** React holds the live demo session. A repository interface plus defensive-copy implementation demonstrates separate town load/save without introducing a database. Reload/reset clear demo state. Restoring a saved world recreates ambient actors without replaying historical effects.
12. **Update scenes without resetting cameras.** `TownRenderer.update` accepts the latest session. Building changes rebuild the static scene inside the existing camera container; chat, residents and effects update without recreating the canvas. Regeneration/reset deliberately remount the scene.

## 2026-10-27 — Foundation

1. **Next.js App Router, React and strict TypeScript.** Establish the intended full-stack application directly in the existing root. Preserve the repository and origin remote; do not initialize Git, commit or push as part of scaffolding.
2. **npm and a committed-in-future lockfile.** Use npm for the requested setup. `package-lock.json` captures the resolved dependency tree for reproducible `npm ci` installs. Node 22+ is the project baseline.
3. **Tailwind CSS 4 with a global component stylesheet.** Tailwind runs through PostCSS. Named component classes express the cohesive village interface; no UI component library or remote fonts are needed.
4. **PixiJS v8, initialized asynchronously in the browser.** React dynamically loads the canvas component without SSR. The rendering implementation imports at effect time. It uses the v8 graphics API and an owned Application/ticker rather than global shared resources.
5. **Explicit renderer lifecycle.** Each scene owns its canvas, observer, ticker and input listeners. Regeneration remounts the keyed canvas. Cleanup aborts pending setup; an application that finishes initialization after disposal is destroyed immediately. Successfully initialized applications also clean up if scene construction fails.
6. **Serializable model separate from graphics.** `generateTown` imports no renderer/browser code. Mulberry32 supplies deterministic local randomness. Generation and Mayor route choices use independent PRNG streams. Regeneration uses browser crypto only to choose the next seed.
7. **Constrained procedural generation first.** A fixed plaza/road/block scaffold guarantees connected access. Seeded variations affect architecture, colors, tree sizes, planting and small home offsets. Twelve homes and reserved expansion space provide a useful foundation before arbitrary roads, terrain or incremental growth.
8. **Mayor is the companion.** The companion is an in-world cat-like Mayor, with Town Hall as headquarters. This is a product character, not a ChatGPT Work pet. The first placeholder is drawn in code; the static portrait uses inline SVG. Rich art and streamer selection/name settings are future work.
9. **Simple autonomous behavior.** The Mayor chooses graph neighbors, avoids immediately reversing where possible, pauses at destinations and animates with frame-time-independent movement. Plaza routes avoid the fountain. Reduced-motion preference disables decorative motion. Complex AI, naps and event reactions are deferred.
10. **Camera independent of town data.** Uniform scaling and translation provide bounded panning, pointer-centered zoom and fit-to-town, with resize handling, touch buttons and keyboard alternatives. Pinch zoom and selection are future enhancements.
11. **No backend or secrets in the prototype.** There is no mocked authentication, no request for Twitch credentials and no integration client. `.env.example` contains optional public labels only. `.gitignore` excludes local env files, caches, outputs, keys and credentials.
12. **Durability will require a versioned generator.** Persistence is deliberately deferred. Reload returns the starter seed. Before saving real towns, persist generator version plus seed and explicit ownership/customization, and define migrations.

## Validation approach

Use ESLint, Next route generation plus TypeScript, production build and focused Node tests for generation, simulation and authentication boundaries. Chrome smoke checks of login, the real WebGL scene, regeneration and camera are manual; do not run automated browser interaction testing for Prompt 003. Town visuals remain programmatic; Twitch avatars are the only new external images.
