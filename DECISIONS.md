# Technical decisions

## 2026-10-31 — Community import and verified live follows (Prompt 018)

1. Add only `moderator:read:followers` as a new scope. Keep identity-only viewer login and preserve supported chat/subscription grants on each upgrade. Bind upgrades to the same authenticated Twitch user; do not accept a browser-selected target channel.
2. Reuse subscriber synchronization and the existing server event transaction for all membership/housing. Followers use a stable per-town import receipt; live events retain Twitch delivery IDs. Reimports cannot allocate a second house or replace customization. Historical imports suppress effects/tasks and mark newly added members as established for both Overview and OBS; genuinely new live followers use the existing arrival behavior.
3. Persist the import job in existing canonical town JSON through revision-checked RPCs, not a new table or an in-memory progress fallback. A five-minute renewable run-ID lease rejects concurrent claims/stale progress. Restart recovery is an explicit idempotent rescan, not a supposedly durable in-memory cursor. Successful member commits and progress checkpoints are separate transactions, so interrupted counters can lag until retry. Tests exercise this with the existing disposable PostgreSQL schema.
4. Bound follower pages to 100 identities, at most 500 pages/10,000 followers/ten minutes; bound network retries to four attempts and rate-limit waits to 30 seconds. Refuse total-only/invalid identity responses and incomplete pagination. Subscriber sync keeps its existing API/error/entitlement rules. Existing whole-world persistence capacity can stop a large import before these limits; report incomplete rather than fabricate a complete community.
5. Extend the existing socket registry with type-specific versions and `channel.follow` v2 conditions. Keep readiness dependent on successful subscription creation; reuse migration/reconnect handling and durable event deduplication. The live follow queue is bounded and transient; reconnect/resync after restart. Distributed durable event workers and optimized large-community batch writes remain deferred.

## 2026-10-31 — Adaptive resident density (Prompt 017C)

1. Replace the global oldest-24 actor pool with one actor per recorded resident up to 256. Above that bound select round-robin across populated technical districts. Keep pool identity independent of camera movement; hydrate near homes/within populated districts and preserve existing actor state at synchronization. This budget covers all 0–200 scenarios without claiming a hardware FPS guarantee.
2. Keep bounded model movement running offscreen; skip resident drawing/interpolation outside screen-space overscan. Use 96px entry/160px exit margins plus a short fade-in rather than destroying/reallocating graphics on camera movement. Spotlight without a town background suppresses all resident drawing. Existing renderer/model timers, scenery and Mayor animations remain.
3. Production OBS previously received four ambient actors, not the recorded 24-actor roster. Add a separate authorized visual roster, bounded to 256, with HMAC identities using a private random per-process key. Never use the browser-visible OBS token as the HMAC key. Keep sanitized world residents empty. Rotate epoch on restart and rehydrate without arrivals; no durable state, new secret configuration or public visitor exposure.
4. Validate model counts, identity/distribution/privacy, resource bounds and camera math with synthetic tests. Browser/OBS/WebGL profiling remains manual at 1920×1080. Sampling above 256, temporary newcomer clustering and independent view clocks are documented tradeoffs, not population/ownership changes.

## 2026-10-29 — Production preparation (Prompt 011A)

1. **Use one paid, continuously running Render Node service with existing Supabase.** Railway with sleeping disabled is a viable alternative. Keep auth timers, sync jobs and outbound EventSub sockets together; no worker or Redis is required for the supervised demonstration. Do not deploy to ordinary serverless functions or multiple replicas.
2. **Persist encrypted auth through private RPCs.** Migration 006 adds a bounded singleton snapshot of HMAC session keys, public profiles, scopes, expiry and authenticated ciphertext. No plaintext credentials or raw browser session IDs are stored. Only service_role executes claim/check/save; direct table access and browser RPC access remain revoked. Existing world/OBS schema is untouched.
3. **Fence old processes rather than merge concurrent snapshots.** Replacement claims invalidate old writers; writes serialize within the active process and must finish before login/logout success. This deliberately trades a brief deploy interruption for simple single-instance recovery. Previews/local durable auth must use a separate database. Distributed coordination remains deferred.
4. **Retain existing auth protections.** Restore forces Twitch validation, sessions expire absolutely after eight hours, and refresh/revocation remain server-side. Save rotated credentials before subsequent validation. Transient outages deny access without erasing refresh credentials/cookies; invalid identity and revocation still terminate sessions. Rotation and PostgreSQL cannot be atomic across services, so rare crash gaps may require reauthentication.
5. **Make EventSub recovery explicit.** OAuth state and sockets remain memory-only. Restart interrupted OAuth from the login button; manually reconnect chat/subscriptions and sync current members after deployment. Existing reconnect, subscription confirmation, channel authorization and receipt deduplication are reused. No fabricated readiness or historical replay.
6. **Require public deployment configuration.** Public HTTPS, durable storage and simulator exclusion are checked; local production retains its exact localhost exception. Bounded global/hashed-credential API budgets avoid trusting arbitrary forwarded IPs. They are demonstration abuse limits, not distributed DDoS protection. Health exposes only status and checks durable-store ownership/reachability.
7. **Keep deployment manual and reviewable.** Render blueprint and DEPLOYMENT.md prepare configuration, migrations, recovery and rollback without executing them. Tests use synthetic credentials/disposable PostgreSQL. Real HTTPS cookies, Twitch delivery, OBS capture and hosting logs remain manual release checks.

These decisions supersede earlier memory-only session/deployment notes. The Mayor remains the companion, and no new gameplay or visual features are introduced.

## 2026-10-29 — OBS presentation (Prompt 010)

1. **Reuse the town and Mayor model.** OBS receives a visual projection of the actual canonical snapshot and advances one existing transient runtime. Spotlight draws the configured Mayor again as a foreground view, sharing the same identity, personality and celebration state; it does not create another character or persistent town. Local movement is not synchronized pixel-for-pixel between separate browser views.
2. **Store display settings outside world commits.** Migration 005 adds a town-keyed display record with mode, side, background and scale. Settings cannot race subscriber allocation by submitting stale world snapshots. Last successful settings write wins; rotating/revoking access does not overwrite settings. Existing tables/functions/migrations are unchanged.
3. **Use a revocable read-only capability.** Generate 32 random bytes server-side, persist only SHA-256, and bind one active grant to one town. The owner obtains the raw key once. It lives in the OBS URL fragment and is sent only in the Authorization header on same-origin reads; it is never a Twitch or administrative credential. Do not log headers, copy private URLs into public channels or embed keys in bundles. Revoke/rotate invalidate the prior key on the next poll. Grants intentionally have no automatic expiry so OBS does not break mid-stream; owners control their lifetime.
4. **Keep database RPC boundaries narrow.** RLS and revoked direct privileges protect display records. Only service_role can execute the two SECURITY DEFINER entry points with empty search_path. The management RPC checks the session-derived owner and locks the town row; the read RPC checks the capability hash. Backend management additionally enforces session, origin, CSRF and strict input shape. The browser has no direct database access and cannot submit a world snapshot or owner claim.
5. **Poll existing backend state.** One non-overlapping poll every three seconds after completion validates access, returns settings/activity and includes geometry only on revision changes. It neither starts Twitch connections nor processes subscriber events. Missing/disconnected sources are shown explicitly; outages retain last saved visuals while activity decays. A long-running single Node process remains required for live Twitch connections. No new credentials, dependencies or scopes.
6. **Keep reactions presentation-only.** Typed priorities cover subscriber/resub/gift, neighborhood and future raid/Bits/donation reactions. Higher priority interrupts; equal/lower waits in a bounded queue; duplicate/expired work is dropped and motion returns to idle. Only existing committed subscriber/expansion presentations feed the adapter. Generic labels omit private event details. Elaborate ceremonies and new live event integrations remain deferred.
7. **Preserve renderer lifecycle.** Overlay options extend the existing renderer, with resize-aware framing, current expansion bounds, smooth follow and temporary focus. Spotlight adds only Mayor graphics, not a second world simulation. Polls/timers/requests and Pixi resources are disposed on unmount or revoked access. Existing interactive camera controls remain the default for website views.

## 2026-10-27 — Real Twitch chat (Prompt 004)

1. **Incremental permission through the existing auth system.** Basic login stays scope-free. A same-origin, CSRF-protected chat authorization action requests only `user:read:chat`, binds OAuth state to the signed-in Twitch ID, and checks granted scopes before issuing the replacement session. Validation/refresh update the stored scopes. No bot, posting, moderation, follower or subscription scopes are requested.
2. **One Node process, one connection per broadcaster.** Reuse the encrypted auth store instead of duplicating it in a worker. A process-wide ChatManager lives outside React/request lifetimes, survives module reloads and has an independent one-second watchdog. Node's native WebSocket requires no added dependency or separate startup command. This is deliberately limited to the existing single-process runtime; a production worker needs shared encrypted sessions and connection leases first.
3. **Follow Twitch's socket protocol.** Wait for welcome before creating `channel.chat.message` with its session ID and a user token. Derive both broadcaster/user conditions from authenticated identity. Let native WebSocket handle ping/pong and never send application frames. Lost sockets use bounded exponential backoff with jitter and recreate subscriptions. Server-directed reconnects use the exact trusted Twitch WSS URL, retain the old socket through replacement welcome and transfer subscriptions without recreation.
4. **Own-channel connection is not town administration.** Control endpoints derive the channel solely from the validated session; status is private to that same account. A personal `twitch:<ID>` preview is not durable ownership of a town. Existing repository-based administration guards remain unchanged. Sign-out, expiry, missing scope or EventSub revocation terminate the connection; tabs share it, and a disconnect affects all tabs for that channel.
5. **Reuse CHAT_MESSAGE and protect content.** Map stable chat message IDs and numeric Twitch identities after checking channel/type/version/session/subscription. Use the existing processEvent/activity rules. HMAC the existing normalized text with a per-feed ephemeral key before processing; retain only fingerprints/chatter IDs for the 60-second spam window. No readable chat history, follower/subscriber records or houses are created. Duplicate IDs use a bounded ten-minute window; live outcome/activity caps avoid unbounded runtime growth.
6. **Project activity into the existing renderer.** Authenticated polling once per second returns sample ages, not chat messages or user tokens. The browser advances the existing simulation between updates, so decay remains smooth. Four generic transient ambient actors reuse existing artwork and movement without becoming residents. Live/demo sessions remain separate and are clearly labeled. Live updates preserve the camera/layout; switching source opens a separate town view. Regeneration changes only local visual layout.
7. **Keep tests offline and operations explicit.** Inject clocks, sockets, credentials and subscription APIs. Cover permission upgrades, HTTP authorization, routing, retries, keepalives, revocation, scope loss and source separation. No browser automation or real user credentials in tests. No EventSub event type beyond chat, persistence, Socket.IO or renderer replacement is introduced.

## 2026-10-27 — Secure Twitch account connection

These decisions supersede the foundation's no-authentication/no-secrets scope. Existing Mayor behavior, renderer, generation and event simulation are preserved.

1. **Use Twitch's server-side Authorization Code flow.** The registered application is Living Town. Credentials and code exchange stay in the Node runtime. Request an empty scope list and use Helix Get Users for basic identity; no email, chat, moderation or subscription permissions. Verify the token's client ID and numeric user ID before accepting the profile.
2. **Separate browser binding from OAuth state.** Generate independent cryptographically random 256-bit state and HttpOnly browser binding values. Store their HMAC digests server-side for ten minutes, with atomic consume-before-exchange semantics. Failed/denied callbacks also consume the attempt. Never accept caller-supplied redirect destinations or expose upstream error details.
3. **Choose server-side sessions, not client-carried OAuth tokens.** The server-storage alternative avoids a JWT/session library for this deliberately ephemeral phase. A browser receives only a random 256-bit session ID, while the memory store retains its keyed digest. Eight-hour absolute expiry bounds access; fresh login rotates the browser session. Cookies are host-only, HttpOnly and SameSite=Lax; production uses Secure `__Host-` cookies and requires an HTTPS redirect.
4. **Encrypt tokens even in the temporary store.** AES-256-GCM uses fresh 96-bit nonces and session-record-specific associated data. HKDF derives separate encryption and HMAC keys from a random 32-byte base64 `SESSION_SECRET`. Access and rotated refresh tokens stay server-side. The authenticated payload is not placed in a browser cookie. No credentials are logged or committed.
5. **Validate maintained sessions independently of browser activity.** Validate on login, startup re-entry and stale reads. A one-minute background scheduler checks the 30-minute freshness threshold, leaving margin inside Twitch's hourly requirement. Cap sessions at 200 and batch checks with bounded concurrency. Authorization guards force a fresh check. Unexpected revocation or a validation outage fails closed. After a known expiry, refresh reactively on an invalid-token response, validate the replacement and retain its rotated refresh token. Concurrent reads of a session share validation work.
6. **Sign out locally before remote cleanup.** Require a same-origin POST with a session-bound CSRF token. Invalidate all sessions sharing the access token and attempt Twitch revocation. Failures enter an encrypted, in-memory retry queue for up to one hour; process shutdown loses that queue. A late validation response cannot resurrect a removed session.
7. **Treat authentication, ownership and subscription as separate facts.** Both streamers and viewers use the same login. Stable Twitch IDs identify accounts; display names and broadcaster profile types grant nothing. `requireTownOwner` validates the session, loads the specified town from a trusted repository and compares its streamer ID. The demo remains public and synthetic; no ownership is assigned on login and no active subscription is inferred. Future mutation endpoints must invoke the guard and their own CSRF protection.
8. **Retain explicit runtime limits instead of adding persistence.** Auth supports one continuously running Node process. Restart or secret rotation invalidates all sessions. Production scaling/serverless needs atomic shared session/state storage, refresh coordination, validation scheduling and durable ownership before deployment. Supabase, live EventSub and backend town mutations remain out of scope.
9. **Keep identity out of static town state.** A small client account widget fetches only the public profile and logout CSRF value from a no-store endpoint. `/account` adds profile and safe error messages. The town's build-time simulator gate and renderer lifecycle remain unchanged. Next dev logging excludes callback URLs; hosting/proxy logs must separately redact OAuth query strings and authorization data.
10. **Test the security boundary without real credentials or browser automation.** Inject clocks, Twitch clients and memory stores. Test state/replay, HTTP cookie protections, callback failures, expiry, encryption tampering, refresh/revocation races and cross-town authorization. Preserve all original simulation/generator tests. A real login and Chrome regression checks are manual.

References: [authorization code flow](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/#authorization-code-grant-flow), [token validation](https://dev.twitch.tv/docs/authentication/validate-tokens/), [refresh](https://dev.twitch.tv/docs/authentication/refresh-tokens/) and [revocation](https://dev.twitch.tv/docs/authentication/revoke-tokens/).

## 2026-10-27 — Town functionality and event simulation

These decisions extend the foundation below; simulation behavior is now owned by the domain layer rather than the renderer.

1. **Keep the Town Overview.** Preserve the generator, original 12 home coordinates and procedural visual language. No isometric renderer or major redesign.
2. **Separate durable world from transient runtime.** `TownWorld` carries schema/generator versions, town/streamer identity, layout, districts, plots, buildings, ownership, residents, Mayor identity and delivery/gift ledgers. `TownRuntime` carries activity, actor behavior, effects and clock. Both are JSON-safe; only the world crosses the future persistence boundary.
3. **Use world coordinates and semantic appearance.** Camera scaling never changes model coordinates. Colors, architecture and decoration IDs are asset-independent. `overviewOf` translates the shared model to the original graphics shapes; future renderers can project the same world.
4. **Pure events and explicit time.** `processEvent` returns a new session and outcome; `tickTown` advances behavior/decay with an injected clock. Neither imports React, PixiJS nor browser APIs. The React demo updates at 100 ms; PixiJS interpolates presentation independently.
5. **Stable ownership and finite capacity.** Fill two expansion plots, then assign original unclaimed demo homes without relocation/restyling. One home per Twitch user per town. At 14 owners, keep subscribers on an explicit waitlist instead of moving buildings or inventing terrain. Resubscriptions reconcile missing initial records and keep maximum cumulative months.
6. **Delivery and semantic deduplication.** Persist processed event IDs in the world snapshot and retain owner uniqueness independently of event ID. Retried deliveries return the original result marked duplicate, with no new effect. Production will need transactional uniqueness and an event retention policy; the in-memory ledger is intentionally unbounded for this demo.
7. **Explicit gift correlation.** A stable group ID joins aggregate and recipient events. Count each group using maximum announced total versus unique identified recipients. Do not create recipients for anonymous aggregates or correlate by timing alone. The future Twitch adapter must establish trustworthy group IDs; there is no live adapter yet.
8. **Anti-spam activity.** A 60-second linearly decaying window, one credited message per user per 10 seconds, identical normalized-message suppression, and a 100-point cap. Transient samples hold normalized text; world snapshots do not. Activity increases resident/Mayor movement and reduces idle pauses.
9. **Mayor remains the companion.** Graph routing and task transitions live in `behavior.ts`. The renderer shows wandering, approach and celebration states. New homes enqueue visits; raids briefly prioritize Town Hall. Runtime queues/effects are bounded, and reduced-motion users see static actor presentation while logical state continues.
10. **Production simulator opt-in is explicit.** Server-provided gate: development, or `TOWN_DEMO_MODE=true` during build. No public event endpoint exists. A future backend must enforce authorization independently; a demo flag is not a security boundary for durable writes.
11. **Temporary in-memory persistence boundary.** React holds the live demo session. A repository interface plus defensive-copy implementation demonstrates separate town load/save without introducing a database. Reload/reset clear demo state. Restoring a saved world recreates ambient actors without replaying historical effects.
12. **Update scenes without resetting cameras.** `TownRenderer.update` accepts the latest session. Building changes rebuild the static scene inside the existing camera container; chat, residents and effects update without recreating the canvas. Regeneration/reset deliberately remount the scene.

## 2026-10-27 — Foundation

1. **Next.js App Router, React and strict TypeScript.** Establish the intended full-stack application directly in the existing root. Preserve the repository and origin remote; do not initialize Git, commit or push as part of scaffolding.
2. **npm and a committed-in-future lockfile.** Use npm for the requested setup. `package-lock.json` captures the resolved dependency tree for reproducible `npm ci` installs. Node 22+ is the project baseline.
3. **Tailwind CSS 4 with a global component stylesheet.** Tailwind runs through PostCSS. Named component classes express the cohesive village interface; no UI component library or remote fonts are needed.
4. **PixiJS v8, initialized asynchronously in the browser.** React dynamically loads the canvas component without SSR. The rendering implementation imports at effect time. It uses the v8 graphics API and an owned Application/ticker rather than global shared resources.
5. **Explicit renderer lifecycle.** Each scene owns its canvas, observer, ticker and input listeners. Regeneration remounts the keyed canvas. Cleanup aborts pending setup; an application that finishes initialization after disposal is destroyed immediately. Successfully initialized applications also clean up if scene construction fails.
6. **Serializable model separate from graphics.** `generateTown` imports no renderer/browser code. Mulberry32 supplies deterministic local randomness. Generation and Mayor route choices use independent PRNG streams. Regeneration uses browser crypto only to choose the next seed.
7. **Constrained procedural generation first.** A fixed plaza/road/block scaffold guarantees connected access. Seeded variations affect architecture, colors, tree sizes, planting and small home offsets. Twelve homes and reserved expansion space provide a useful foundation before arbitrary roads, terrain or incremental growth.
8. **Mayor is the companion.** The companion is an in-world cat-like Mayor, with Town Hall as headquarters. This is a product character, not a ChatGPT Work pet. The first placeholder is drawn in code; the static portrait uses inline SVG. Rich art and streamer selection/name settings are future work.
9. **Simple autonomous behavior.** The Mayor chooses graph neighbors, avoids immediately reversing where possible, pauses at destinations and animates with frame-time-independent movement. Plaza routes avoid the fountain. Reduced-motion preference disables decorative motion. Complex AI, naps and event reactions are deferred.
10. **Camera independent of town data.** Uniform scaling and translation provide bounded panning, pointer-centered zoom and fit-to-town, with resize handling, touch buttons and keyboard alternatives. Pinch zoom and selection are future enhancements.
11. **No backend or secrets in the prototype.** There is no mocked authentication, no request for Twitch credentials and no integration client. `.env.example` contains optional public labels only. `.gitignore` excludes local env files, caches, outputs, keys and credentials.
12. **Durability will require a versioned generator.** Persistence is deliberately deferred. Reload returns the starter seed. Before saving real towns, persist generator version plus seed and explicit ownership/customization, and define migrations.

## Validation approach

Use ESLint, Next route generation plus TypeScript, production build and focused Node tests for generation, simulation and authentication boundaries. Chrome smoke checks of login, the real WebGL scene, regeneration and camera are manual; do not run automated browser interaction testing for Prompt 003. Town visuals remain programmatic; Twitch avatars are the only new external images.
